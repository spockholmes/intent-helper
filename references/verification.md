# 测试验证（Verification）

## Why

确保结果正确——确认意图被正确理解、代码符合预期。


## 验证阶段

**执行检查**：进入验证流程时，先判断是否需要造数。如果需要，必须先完成造数再执行操作，不能跳过。

按阶段推进，每个阶段记录验证报告。

### 阶段一：单元测试（验证单个环节）

验证方法/函数是否符合意图。

- 读取意图文档，生成测试用例
- 用例对应意图规则，覆盖边界条件
- 跑通测试，迭代修复

### 阶段二：准备数据（判断是否需要）

**什么时候需要造数？**

| 情况 | 是否需要造数 |
|------|------------|
| 验证逻辑依赖特定数据（如某状态、某金额） | 需要 |
| 验证批处理/定时任务（依赖底层数据） | 需要 |
| 验证端到端流程（需要完整数据链路） | 需要 |
| 纯逻辑单元测试（用 mock） | 不需要 |
| 仅做意图文档比对（静态检查） | 不需要 |

**判断原则**：如果验证需要真实数据参与，就必须造数，不能跳过。

涉及底层数据时，先造数。

**两种造数方式**：
- 依据意图文档造数（不看实现）→ 验证代码与意图一致性
- 依据代码入口造数 → 验证具体代码逻辑

**操作**：写造数脚本 → 执行到数据库

### 阶段三：执行操作

按验证范围串联操作：

| 类型 | 操作方式 |
|------|---------|
| 后端 | 调用 API |
| 前端 | 浏览器访问，操作页面 |
| 脚本 | 直接运行 |
| 批处理 | 触发执行（依赖底层数据时先造数） |
| 定时任务 | 触发执行 |

### 阶段四：验证结果

- 每个环节的结果
- 最终端到端的结果
- 对比实际与预期，确认是否正确


## 验证范围

| 范围 | 覆盖阶段 | 适用场景 |
|------|---------|---------|
| **单点验证** | 阶段一（单元测试） | 只验证一个方法/接口/页面 |
| **联合验证** | 阶段一至四 | 多个环节串联，验证完整流程 |


## 环境信息获取

- **需要时**：查用户层知识库（见 `wiki.md` 的查阅方式）
- **缺失时**：询问用户，可提议沉淀到用户层


## 报告存放

```
.project-info/test-data/YYYYMMDD-描述/
├── unit-test-report.md         # 单元测试报告
├── data-setup.sql              # 造数脚本（如需要）
├── data-setup-result.md        # 造数结果
├── execution-log.md            # 执行日志
└── verification-report.md      # 最终验证报告
```


## 交互示例

### 示例一：单点验证（只做单元测试）

**用户**："为积分发放功能生成单元测试。"

**AI**：
> 读取意图文档，生成测试用例：
> - 正常发放：实付 100，应发 80 分
> - 上限验证：实付 1000，应发 500 分
> - 边界：实付 0，应发 0 分
>
> 判断：纯逻辑验证，用 mock，不需要造数。
>
> 测试已跑通，报告保存至 `.project-info/test-data/20260910-积分发放/unit-test-report.md`。

### 示例二：联合验证（单元测试 → 造数 → 批处理 → 页面验证）

>
