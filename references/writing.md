# 意图文档编写（Writing）

## Why

将模糊需求沉淀为结构清晰的意图文档，让 AI 能准确执行，让人能高效审核。


## 核心规则

### 总-分结构（按复杂度自然浮现）

| 复杂度 | 结构 |
|--------|------|
| 简单 | 单文档（`总览.md`）写清楚即可 |
| 复杂一点 | `总览.md` + 一个子目录，所有子文档平铺在同一个子目录下 |
| 再复杂 | 按意图建多个子目录，子文档分门别类放置 |

**结构随意图梳理逐步调整**：开始时可能一个文档就够，随着内容增多，逐步拆出子文档；子文档多了，再按意图建不同的子目录。不强求一开始就定好结构，也不强求一定拆到几层。

**总-分结构对 AI 和人同样友好**：AI 先读总览就能抓住主线；人也先读总览了解全局，需要细节再往下翻。改某个子项时也不影响整体。

### 目录结构示例

**简单**：
```
20260901-积分发放/
└── 总览.md
```

**复杂一点**（总览 + 一个子目录，子文档平铺）：
```
20260901-积分系统/
├── 总览.md
└── 功能模块/
    ├── 积分发放.md
    ├── 积分抵扣.md
    └── 积分过期清理.md
```

**再复杂**（按意图建多个子目录）：
```
20260901-积分系统/
├── 总览.md
├── 功能模块/
│   ├── 积分发放.md
│   ├── 积分抵扣.md
│   └── 积分过期清理.md
└── 对外接口/
    ├── 积分查询接口.md
    └── 积分发放接口.md
```

### 子目录命名（按意图命名）
子目录名应表达它所包含内容的意图，而不是套用固定模板。

根据意图类型命名：
- 按功能意图拆 → 以功能命名，如 `功能模块/`
- 按接口意图拆 → 以接口命名，如 `对外接口/`
- 按技术方案意图拆 → 以方案命名，如 `技术方案/`
- 按迁移意图拆 → 以迁移内容命名，如 `数据迁移/`
- 其他 → 按该层的实际意图命名（kebab-case）

**原则**：子目录名一看就知道里面装的是什么意图的内容。

### 剪裁原则
- **原则**：如无必要，勿增实体——不必要的内容不加，必要的内容尽量精简
- **不写**：AI 已知的通用语法、框架默认行为、业界通用规范、具体实现代码
- **只写**：项目特有的规则、非默认的架构决策
- **视角**：站在 AI 这一侧，以"AI 执行任务所必需"为判断标准

### 双可读性要求
- **对人友好**：自然语言表达，逻辑清晰，核心信息靠前
- **对 AI 友好**：关键概念显式化（表名/字段名明确写出），口径精确无歧义，引用给出明确路径


## 工作流程

### 策略一：信息较完整时 → 先出草稿，再逐项澄清

用户已提供较完整的信息时，直接基于已有信息生成草稿。

**草稿原则**：忠于用户原文，保持内容一致，不擅自补充。

生成草稿后，按总-分结构的层级逐项澄清。每次只问一个位置，说清楚位置后再问问题。

**示例**：
> 已生成草稿，保存至 `.project-info/coding/20260901-积分系统/`。
>
> 总览.md → 范围：后续会扩展到抵扣和兑换吗？

（用户回答后）

> 功能模块/积分发放.md → 数据来源：实付金额来自哪个表？

（用户回答后）

> 功能模块/积分发放.md → 上限规则：单笔上限有吗？多少？


### 策略二：信息较少时 → 先追问关键信息，再出草稿

用户信息不足以支撑一份有效草稿时，先主动追问关键信息。

追问时不涉及文档位置（因为还没有文档），只说问题本身。

**示例**：
> 当前信息还不足以生成完整草稿，先确认几个关键信息：
>
> 1. 积分按什么基数计算？实付金额还是商品总价？
> 2. 有单笔上限吗？
> 3. 退款时积分要扣回吗？
> 4. 这个功能是独立的还是积分系统的一部分？
>
> 请逐项补充，我再生成草稿。


### 表结构联动

意图梳理过程中，如果涉及数据表：

**已有表**：
- 读取表文档，在意图文档中生成相对路径引用
- 只引用关键字段名（剪裁）

**新表**：
- 主动询问："该表尚未录入知识库，需要现在设计吗？"
- 用户确认 → 按 [wikis/table.md](../wikis/table.md) 的流程引导设计
- 生成表文档，保存至 `.project-info/wikis/table-wiki/表定义/`
- 更新 `.project-info/wikis/table-wiki/总览.md` 索引
- 在意图文档中生成相对路径引用

**表结构变更**：
- 检测到变更时，同步更新表文档


## 变更流程

### 步骤1：变更识别
用户提出变更时，识别类型：
- 参数调整（比例、上限、条件）
- 范围扩展（新增子任务）
- 范围缩减（废弃功能）
- 结构重组（拆分/合并）

### 步骤2：影响分析
在对话中列出受影响文档、章节、SQL 片段。

### 步骤3：变更预览
展示"旧 vs 新"对比，供用户确认。

### 步骤4：直接覆盖
用户确认后，更新文档为当前有效版本，**不追加变更记录**。

### 步骤5：提示提交
"文档已更新。建议使用 `git commit` 记录本次变更。"


## 文档模板

### 总览文档（`总览.md`）

```
# [系统/模块/方案] - 总览

## 1. 背景与目标
> 简述为什么要做，解决什么问题。

## 2. 范围
> 包含哪些内容，明确边界（不含什么）。

## 3. 子任务索引
> - [子任务A](./功能模块/子任务A.md) – 简述
> - [子任务B](./功能模块/子任务B.md) – 简述

## 4. 全局约束（如有）
> 性能指标、技术选型、通用规则等。
```

### 子文档模板

```
# [子任务名称]

## 背景
> 简述本子任务的目的。

## 触发条件与输入
> 何时开始、需要什么输入信息。

## 核心规则
> - 规则描述。
> - **口径说明**：关键概念含义、判断条件、单位等。
> - **数据来源**：`[待引用]`
> - **复杂逻辑**：参见附录。

## 特殊约束（如有）
> 性能、安全、兼容性等要求。

## 输出与结果
> 产出什么内容、什么格式。

## 附录（如有）
### 附录：XXX {#appendix-xxx}
> 用途、关键信息说明。

[SQL 或伪代码]
```

### 单文档模板（`总览.md`）

```
# [任务名称]

## 背景与目标
> ...

## 详情
> 做什么、触发条件、输入输出、口径、规则。

## 特殊约束（如有）
> ...

## 数据来源
> `[待引用]`

## 附录（如有）
### 附录：XXX {#appendix-xxx}

[SQL 或伪代码]
```


## 交互示例

### 示例一：涉及已有表

**用户**："我要设计一个积分系统，包含发放、抵扣、过期清理三个功能。数据来自 orders 表。"

**AI**：
> 已生成草稿，保存至 `.project-info/coding/20260901-积分系统/`。
>
> 结构（复杂一点，一个子目录）：
> - `总览.md`
> - `功能模块/积分发放.md`
> - `功能模块/积分抵扣.md`
> - `功能模块/积分过期清理.md`
>
> 总览.md → 范围：后续会扩展到抵扣和兑换吗？

**用户**："目前先做这三个，后续可能加兑换。"

**AI**：
> 功能模块/积分发放.md → 数据来源：orders 表已存在，将引用其 `paid_amount` 字段。上限规则：单笔上限有吗？多少？

**用户**："500分。"

**AI**：所有信息已澄清，文档定稿。建议 `git commit`。

### 示例二：涉及新表

**用户**："我要做积分系统，需要记录每次积分变更的流水。"

**AI**：
> 已生成草稿，保存至 `.project-info/coding/20260901-积分系统/`。
>
> 结构：
> - `总览.md`
> - `功能模块/积分发放.md`
> - `功能模块/积分流水.md`
>
> 总览.md → 范围：后续会扩展到抵扣和兑换吗？

**用户**："暂时只做发放和流水记录。"

**AI**：
> 功能模块/积分流水.md → 表结构：需要记录哪些字段？涉及新表吗？

**用户**："新建一个 point_flow 表，记录用户ID、变动类型、变动积分、变动后余额、来源订单号、时间。"

**AI**：
> 该表尚未录入知识库，需要现在设计吗？

**用户**："需要。"

**AI**：
> 请补充必须信息：
> 1. 表说明：这个表是做什么的？数据来源是本系统生成还是外部同步？
> 2. 每个字段的字段含义、字段名、字段类型、是否可空、是否唯一、默认值、外键、是否索引、备注。
>
> （用户补充后）
>
> 表文档已生成并保存至 `.project-info/wikis/table-wiki/表定义/point_flow.md`，索引已更新。
>
> 意图文档中的引用已生成。

### 示例三：意图变更

**用户**："发放比例从80%改到70%，上限改到1000。"

**AI**：
```
变更影响：
1. 功能模块/积分发放.md → 核心规则数值
2. 附录/SQL片段 → `0.8` → `0.7`，`500` → `1000`

确认修改？
```

**用户**："确认。"

**AI**：文档已更新。建议使用 `git commit` 记录本次变更。
